# Componenta App

Подготовка конфигурации и запуск Componenta-приложений: провайдеры, области запуска, адаптеры, загрузчики и билдеры.

## Установка

~~~bash
composer require componenta/app
~~~

Требуется PHP 8.5.13 или новее. Пакет объявляет `Componenta\App\ConfigProvider` в метаданных Composer; `componenta/composer-plugin` добавляет его в сгенерированный список провайдеров.

Провайдер регистрирует `ApplicationBuildOrchestratorFactory`, фабрики приложения и целевого объекта загрузки, `DateTimeBootloader`, `ClassDiscoveryBootloader` и слушатель классов `BootMethodInvocation`. Конкретные HTTP, CLI и WebSocket реализации подключаются через пакеты интеграции.

## Точка входа

У каждой области запуска свой файл, например `public/index.php` или `bin/console.php`:

~~~php
use Componenta\App\Scope;
use Componenta\Stdlib\PathResolver;

use function Componenta\App\run;

$root = dirname(__DIR__);
require $root . '/vendor/autoload.php';

run(Scope::CLI, new PathResolver($root));
~~~

`run()` меняет рабочий каталог на корень проекта, загружает `config/container.php`, проверяет возвращённый PSR-11 контейнер и передаёт запуск в `Runner`. Runner получает приложение нужной области через `AppFactory`, создаёт отдельный целевой объект загрузки, выполняет загрузчики и только после их завершения запускает приложение.

Провайдер интеграции регистрирует значение области и идентификатор сервиса контейнера в `ConfigKey::APPLICATIONS`:

~~~php
use Componenta\App\ConfigKey;
use Componenta\App\Scope;

return [
    ConfigKey::APPLICATIONS => [
        Scope::HTTP->value => MyHttpApplication::class,
    ],
];
~~~

Сервис должен реализовывать `AppInterface`. Значение области используется как точный ключ, поэтому для пользовательской области нужна собственная регистрация. Фабрика разрешает только выбранный сервис. Адаптер целевого объекта загрузки остаётся самостоятельной точкой расширения: он оборачивает приложение и предоставляет только операции настройки, не возвращает приложение и не раскрывает метод `run()`. Загрузчики получают объект через `BootContext::target(Contract::class)`. Контейнер остаётся доверенной инфраструктурой приложения, а не границей безопасности или изоляции.

## Конфигурация и контейнер

`config/config.php` возвращает `ConfigDefinition`. Провайдеры обрабатываются в порядке регистрации:

~~~php
use Componenta\App\Config\ComposerPackageConfigProvider;
use Componenta\App\Config\ConfigDefinition;
use Componenta\App\Config\DiscoveryDefinition;

return new ConfigDefinition(
    providers: [
        new ComposerPackageConfigProvider(
            $paths->resolve('config/componenta-providers.php'),
        ),
    ],
    discovery: new DiscoveryDefinition(directories: ['src']),
);
~~~

В список добавляются необходимые провайдеры приложения и файлов. Для конфигурации через `#[AsConfig]` подключается `AttributeConfigProvider`. Если `discovery` опущен, обнаружение классов отключено.

В `config/container.php` две части результата подготовки конфигурации передаются в DI:

~~~php
use Componenta\App\Config\ConfigFactory;
use Componenta\DI\ContainerFactory;

$definition = require $paths->resolve('config/config.php');
$result = ConfigFactory::create(paths: $paths, definition: $definition);

return (new ContainerFactory())->create(
    $result->composition->config,
    $result->composition->dependencies,
)->container;
~~~

Runtime `Config` содержит настройки приложения, а `DependencyDefinitions` — регистрации DI. Контейнер получает тот же экземпляр Config. ConfigFactory вызывает провайдеры и в development, и в production.

ConfigFactory регистрирует `PathResolverInterface` и `BuildStore`. При настроенном discovery он выбирает опубликованный `app.discovery` либо общий итератор исходников. Готовая карта исключает обход директорий и токенизацию. Без пригодной публикации обычный запуск читает исходники и не записывает runtime-кеш. `APP_ENV` не меняет алгоритм композиции.

`PreparedBuild` выбирается один раз до вызова провайдеров. Необязательный потребитель проверяет `ConfigKey::PREPARED_BUILD` и получает этот сервис с типом `PreparedBuild`. Проверять `has(PreparedBuild::class)` недостаточно: DI может считать конкретный класс кандидатом для автосборки. Все потребители используют одно выбранное поколение, даже если параллельно публикуется следующее.

`AttributeConfigProvider` создаёт и вызывает провайдеры при каждой композиции. Артефакт `app.config-providers` содержит упорядоченный список имён классов, а не результаты их вызова. Он исключает рефлексию остальных объявлений, сохраняя порядок, ленивые contributions и текущие runtime-значения. При отсутствии метаданных используется выбранный discovery iterator. Сборка не изменяет `config/config.php` и не сериализует полный Config или DI-контейнер.

`source: true` в `ConfigFactory::create()` либо `APP_DISCOVERY_SOURCE=1` до bootstrap отключает prepared metadata. Выбор производится до загрузки определения и провайдеров. Билдеры получают общий исходный discovery через `ConfigKey::DISCOVERY_SOURCE`. Для каждой сборки создавайте новую source-композицию; повторное использование контейнера не является наблюдением за изменениями файлов.

## Единый протокол сборки

Участник владеет ID и схемой своего артефакта и реализует один интерфейс:

~~~php
use Componenta\App\Build\ApplicationBuilderInterface;
use Componenta\App\Build\BuildContext;

final readonly class MetadataBuilder implements ApplicationBuilderInterface
{
    public function __construct(private MetadataSource $source) {}

    public function build(BuildContext $build): void
    {
        $build->write('my-app.metadata', $this->source->metadata(), schemaVersion: 1);
    }
}
~~~

Сервисы участников регистрируются списком `ConfigKey::BUILDERS`. Фабрики DI передают исходные зависимости; конструкторы ничего не записывают. Оркестратор проверяет весь список и разрешает все сервисы перед первым `build()`. Пустой список допустим и публикует пустое поколение.

`BuildContext::write()` синхронно сериализует данные в ещё не опубликованное поколение. Поддерживаются массивы, скаляры и enum cases. Неподдерживаемое runtime-значение немедленно вызывает ошибку. Участник может обработать известную ошибку переносимости и вызвать `skip($id, $reason)`, явно сохранив свой source fallback. Остальные ошибки должны прерывать сборку. Повторный ID, недопустимый ID и запись после публикации запрещены. Контекст предоставляет право записи только на время текущей сборки: его нельзя клонировать или сериализовать, а после публикации или ошибки он закрывается. Участники не читают результаты друг друга в текущем запуске, не выбирают активные пути и не выполняют внешние миграции через этот протокол.

После завершения всех участников сохраняется manifest, затем атомарно заменяется `var/cache/build/current.json`. До этой операции новые процессы видят прежнее полное поколение. Ошибка останавливает дальнейшие шаги и сохраняет активную публикацию. Произвольные внешние эффекты протокол не откатывает. Файлы располагаются в `var/cache/build/generations/<generation>/`; участники не управляют этими путями.

| ID | Содержимое |
| --- | --- |
| `app.discovery` | Объявления с файлами, именами, типами и модификаторами |
| `app.config-providers` | Упорядоченные имена провайдеров `#[AsConfig]` |
| `app.boot` | Имена публичных методов с `#[Boot]` по классам |

Интеграционные пакеты владеют дополнительными ID. `PreparedBuild::read($id, $schemaVersion)` возвращает `null` для отсутствующего, пропущенного, нечитаемого либо несовместимого необязательного артефакта. Пакет может использовать source fallback. Причины пропуска доступны через `skipped()`.

### Свежая среда сборки

`ApplicationBuildRunner` создаёт source-конфигурацию и новый DI-контейнер, затем запускает оркестратор. На время композиции он переходит в директорию приложения, после чего восстанавливает рабочий каталог вызывающего кода. Runtime bootloaders и методы `#[Boot]` не запускаются. Поэтому новый `#[AsConfig]` может добавить билдер в том же запуске сборки, пока прежнее поколение остаётся активным.

~~~php
use Componenta\App\Build\ApplicationBuildRunner;

$prepared = ApplicationBuildRunner::build(
    paths: $paths,
    definition: static fn () => require $paths->resolve('config/config.php'),
);
~~~

`componenta/app-console` предоставляет `app:build`. Ранний dispatcher сборки должен выполняться до обычного runner: устаревшая runtime-конфигурация и boot-эффекты не должны препятствовать запуску сборки. Вызов оркестратора из уже подготовленного runtime-контейнера не даёт такой гарантии свежести.

### Идентичность и обязательные артефакты

Задайте одинаковый `APP_BUILD_ID` для сборки и runtime, чтобы связать публикацию с неизменяемым релизом. Другое значение, включая отсутствие ID при его наличии в сборке, отклоняет публикацию. Без явного ID действует контракт: исходники, зависимости и влияющая на сборку конфигурация неизменны до следующей сборки. При старте не вычисляются хеши всего дерева или времена изменения файлов. Карты сохраняют исходные пути; не переносите их между несовместимыми файловыми корнями.

Обязательные артефакты задаются явно и не выводятся из `APP_ENV`:

~~~php
$result = ConfigFactory::create(
    paths: $paths,
    definition: $definition,
    requiredArtifacts: ['app.discovery', 'app.config-providers', 'router.routes'],
);
~~~

Передайте тот же список в `ApplicationBuildRunner::build(..., requiredArtifacts: [...])`. Отсутствующий либо пропущенный обязательный артефакт остановит публикацию. Явный source-bootstrap игнорирует старую публикацию, сохраняя требование к новой. Runtime-переменная `APP_DISCOVERY_SOURCE=1` вместе с непустой политикой обязательных артефактов отклоняется как противоречие: для подготовки используйте явный source API, для восстановления осознанно снимите runtime-требование. Runtime отклоняет отсутствие публикации, несовпадение identity, нечитаемые данные и несовместимую версию схемы. При строгой политике непригодный core discovery также вызывает ошибку: сброс выбранного поколения не должен обходить обязательные readers. Изменяемый current pointer хранится как JSON; неизменяемые PHP manifest и payload можно кешировать OPcache без проверки timestamp. Пакет отвечает за проверку внутренней структуры своего payload. Эти проверки не доказывают семантику приложения; проверьте prepared runtime до активации релиза.

### Очистка и развёртывание

`ApplicationBuildRunner::clean($paths)` и `app:clean` снимают только текущий указатель. Они не создают билдеры и не выполняют PHP артефактов. Уже работающие процессы сохраняют выбранные поколения. Новые процессы переходят к исходникам либо завершаются ошибкой при обязательной публикации. Успешной пересборке не нужна предварительная очистка.

Старые поколения и незавершённые staging generations сохраняются. Удаляйте их offline, когда ни один worker больше не использует их, либо удаляйте целый отработавший релиз. Online GC не реализован. `ApplicationBuildCleanerInterface` и очистка файлов отдельными участниками удалены.

PHP-карты являются доверенными исполняемыми артефактами. Храните каталог вне публичной директории и предоставляйте запись только deployment-пользователям. Чтение отклоняет symlink-файлы и файлы с правом записи для группы/остальных на POSIX. Публикуйте перед запуском или перезапуском workers. Старые плоские `classes.php`/`boot.php` игнорируются; создайте новую сборку. Формат публикации 2 разделяет имена служебных файлов и допустимые идентификаторы артефактов, включая `manifest`. Перед развёртыванием пересоберите публикации прежних форматов.

## Загрузчики и discovery

Упорядоченный список `ConfigKey::BOOTLOADERS` содержит уникальные имена классов загрузчиков. Провайдер проверяет все регистрации и разрешает сервисы до начала исполнения, затем один раз проверяет `supports()` у каждого кандидата в порядке регистрации. `BootloaderInterface::boot()` получает `BootContext` с текущей областью запуска, типизированным доступом к целевому объекту и `ContainerValue`. При непосредственном вызове `boot()` вызывающий код обязан предварительно проверить применимость. Базовый `Bootloader` поддерживает метод `__invoke()` с внедрением параметров. `DateTimeBootloader` устанавливает `APP_TIMEZONE` (по умолчанию UTC) для HTTP, CLI и WebSocket; неверная временная зона прерывает загрузку.

`ClassDiscoveryBootloader` передаёт рабочий итератор классов в `ClassListenerNotifier`. Слушатели обрабатывают источник, выбранный ConfigFactory.

`#[Boot]` помечает публичные методы запуска. `BootMethodInvocation` собирает их один раз для каждого обнаруженного объявления и при финализации передаёт в `BootInvocationRunner`, который выполняет методы по убыванию приоритета. Повторяемые атрибуты одного метода сохраняют заявленную семантику. В начале финализации слушатель освобождает собранные метаданные и не допускает повторного поиска. Явные параметры могут содержать обычные значения и DI-метаданные: `EntryId` для сервиса, `Config` для настройки и `Env` для значения окружения.

При настроенном discovery `BootBuilder` создаёт `app.boot`: имя класса → упорядоченный список публичных методов с `#[Boot]`, включая наследуемые. Атрибуты и вложенные объекты параметров создаются нативно при каждом запуске. Карта сокращает поиск методов и исключает автозагрузку объявлений без boot-методов; при отсутствии, неверной структуре или несовпадающем поколении используется исходный путь. При выборе исходного discovery старые boot-метаданные игнорируются.

## Пути кеша

BuildStore управляет артефактами внутри `ConfigKey::DEFAULT_CACHE_BUILD_DIR`. Development/runtime-кеши отделены от поколений сборки.

## Пакеты интеграции

- `componenta/app-console` предоставляет Symfony Console и реестр команд.
- `componenta/app-http` предоставляет HTTP-приложение.
- `componenta/websocket-app` предоставляет область запуска WebSocket.
- `componenta/cqrs-app` добавляет CQRS discovery, рабочие карты и билдер.
- `componenta/interceptor-app` добавляет discovery метаданных интерцепторов и билдер.

Runtime-библиотеки могут использоваться самостоятельно; app-пакеты подключают конфигурацию, discovery, билдеры и запуск приложения.

## Измерение производительности

Установите зависимости разработки и запустите PHPBench:

```sh
composer bench
vendor/bin/phpbench run --filter=StartupBench --report=aggregate
vendor/bin/phpbench run --filter=RuntimeBench --report=aggregate
```

Набор измеряет создание конфигурации и контейнера, поиск объявлений, выполнение загрузки и полный запуск для 300 и 1000 объявлений в исходном и подготовленном режимах; формирование конфигурации через атрибуты и список пакетов Composer; сборку и очистку артефактов; разрешение приложения, создание целевого объекта, выбор загрузчиков, разрешение параметров boot-методов и запуск без поиска классов в прогретом контейнере. Подготовка данных и проверки результата вынесены за границы измерения. Для конфигурации через атрибуты отдельно измеряются source и prepared: индекс провайдеров должен загружать только подходящие классы, исходный путь сканирует все объявления. Готовые карты создаются штатными билдерами в отдельном PHP-процессе, поэтому классы не прогреваются в измеряемом процессе. Для холодных сценариев используется одно выполнение на изолированную итерацию, для прогретых — многократные выполнения. По умолчанию отключены CLI OPcache и Xdebug. Сводный отчёт содержит время, память и разброс; в CI используется сокращённое число итераций без порогов скорости.

Для сохранения базового результата используйте `vendor/bin/phpbench run --tag=baseline --report=aggregate`, для сравнения следующего запуска на той же машине — `vendor/bin/phpbench run --ref=baseline --report=aggregate`. Синтетические измерения не включают время запуска процесса PHP и ввод-вывод реального HTTP-приложения; это не измерение TTFB.
